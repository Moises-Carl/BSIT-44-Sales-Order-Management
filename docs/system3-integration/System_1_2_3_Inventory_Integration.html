1. Purpose, scope and ownership

The integration joins Catalogue’s seller offers to Sales’ accepted order items and Inventory’s stock reservations. Catalogue orderability and physical stock availability are separate checks.

SystemOwns / may changeIntegration responsibility
1 · Cataloguecategory, product, seller, seller_offer; names, prices and active statusesProvide stable offer identities and active-status information. No stock balances are stored in Catalogue.
2 · Sales / Ordercustomer, sales_order, order_item, order_status_history; accepted purchase detailsSubmit immutable item references; coordinate reservation, payment, fulfillment and cancellation. Never alter stock balances.
3 · InventoryInventory balances, reservations, movements, request/event audit recordsReserve, confirm, release, expire and deduct stock atomically. Never verify payments or rewrite Sales purchases.
4 · BillingInvoices, payment attempts and verified resultsReport authoritative payment outcomes to Sales. No direct Inventory payment feed is assumed.
5 · DeliveryShipments, dispatch/pickup evidence and delivery confirmationSend an agreed stock-deduction event to Inventory; report verified delivery to Sales.

Initial target scope

  • One seller per order; one stock record per seller offer; whole-unit quantities.
  • All-or-nothing reservation across every item in an order.
  • PHP product totals remain Sales snapshots. Inventory never prices an order.
  • One shipment per order, verified prepayment, and no initial COD or partial fulfillment.

Outside this handoff’s implementation scope

Multi-warehouse operations, purchasing, serial/batch tracking, paid cancellation, refunds and return workflows are not added to Sales. The proposed movement vocabulary retains Inventory’s restock/return/adjustment concepts; it does not enable customer returns in the current Sales app.

Availability is advisory

A displayed quantity is not a promise. Only an authoritative, all-item reservation can authorize the next payment step.

5. Stock invariants and concurrency

available = quantity_on_hand − quantity_reserved
RuleRequired enforcement
Nonnegative balanceson_hand ≥ 0; reserved ≥ 0; reserved ≤ on_hand; whole units only.
Available and low stockCompute availability from balances. Low stock means available ≤ reorder_level; out of stock means available = 0.
Reservation accountingReserved balance equals the sum of active and confirmed reservation quantities. Periodically reconcile; do not overwrite mismatches silently.
Physical movement auditEvery change to on_hand and its movement record commit together. Movements are append-only; correct mistakes with a new movement.
All-item atomicityValidate every order item; if one fails, create no holds and change no reserved balance. Return all known short/inactive item details.
Retention and authorizationDo not delete stock/reservations/movements used by purchases. Only Inventory’s controlled service writes its balances and audit tables.

Single lock order for every mutating operation

  1. Lock the Inventory order-control row for the affected order, creating it safely if absent.
  2. Lock affected inventory rows in ascending inventory_id order.
  3. Lock affected reservation rows in a consistent item order.
  4. Apply validation, balances, reservation states, audit/result and outbox changes; commit.

Reserve, confirm, release, expiry and fulfillment all follow this order. An expiry worker first finds candidate order IDs without holding row locks, then processes each order using the same locking order. This avoids a release-versus-reserve race and reduces deadlocks. Deadlocks still require bounded retry with the original reference.

Balance example

ActionOn handReservedAvailable
Restock 10 units10010
Reserve 3 units1037
Release those 310010
Reserve/confirm 3, then fulfill707

Reservation, confirmation, release and expiry do not change physical on-hand. Fulfillment changes both on-hand and reserved and records a sale movement. Never keep a transaction open while waiting for another service.

7. Cancellation, expiry and race handling

Submitted unpaid cancellation

  1. Sales enters cancellation_pending, records the reason and blocks fulfillment.
  2. Billing authoritatively verifies unpaid cancellation and blocks future charges for that order.
  3. Inventory locks the order-control row and records a reservation-blocked tombstone, even if no reservation exists yet.
  4. Inventory releases eligible holds, reduces reserved balances, saves the terminal result and commits. No physical movement is recorded for release.
  5. Sales marks cancelled only when the unpaid check and no-active-or-future-reservations guarantee are both authoritative.
Race / failureRequired outcome
Release arrives before a delayed reserveThe tombstone makes the later reserve reject. “No holds found right now” is not sufficient release proof.
Payment arrives during cancellationKeep the verified payment evidence, pause progress and reconcile. Do not silently cancel a paid order or ship without valid stock.
Payment arrives after expiryInventory must not revive an expired hold. Sales keeps the order unresolved; agree re-reservation/refund handling outside the initial scope.
Confirm races with expiryBoth lock the same order-control and stock rows. One valid transition wins; the other returns the authoritative current result.
Dispatch races with releaseOnly the agreed eligible state may win. A fulfilled hold cannot be released; a released/expired hold cannot be fulfilled.
Timeout or lost responseThe result is unresolved. Query the original request, or retry the same immutable request reference. Never assume rejection or create a new hold key.

Unpaid expiry

The Inventory group proposes 30 minutes; the duration is not a confirmed class agreement. An Inventory worker expires eligible active holds under locks, reduces only reserved balances, and writes a durable result/notification. Never rely on the customer’s browser timer to change stock.

Lifecycle receiver is implemented locally

Use the signed, versioned POST /api/events/inventory/lifecycle receiver for later expiry, release and fulfillment facts. It validates complete reservation identities, monotonic versions and eligible states. A later lifecycle fact must not overwrite the original reserve operation result. External Inventory delivery remains to be integrated.

Signed messages and retries

Sales queries the original request before sending. An authenticated 404 permits POST of the same payload. {"status":"pending"} remains unresolved. The current HTTP timeout is 10 seconds and dispatch lease is 60 seconds. These are Sales transport settings, not reservation lifetimes.

10. Compatibility and policy decisions

Confirmed validity: local alignment complete

Inventory’s source design defines confirmed holds as non-expiring, represented by expires_at = NULL in the proposed SQL. The Sales confirmation handler, stock guards, simulator and progress display now accept explicit NULL confirmed expiry. Active unpaid holds still require a deadline. Future confirmed expiries remain supported for compatibility with an explicitly expiring provider.

Implemented locally: non-expiring confirmation, semantic event deduplication, order-independent reservation matching, cancellation flag correction and a signed versioned lifecycle receiver. Agree the authoritative validity contract with the real Inventory service and verify it jointly. A separate technical authorization lease may exist only if the groups explicitly design it; it must not be misrepresented as an Inventory hold expiry.

No fabricated compatibility

The simulator now confirms without automatic expiry. Earlier demo records may retain their explicit expiry values; the application preserves those values rather than rewriting historical orders.

Further contract decisions

Contract issueRequired joint decision
Reservation lifecycleConnect Inventory to the implemented /api/events/inventory/lifecycle v1 receiver. Provide monotonic per-order versions, stable event references and complete matching reservation identities.
Failed paymentInventory proposes release on failure; the current Sales flow flags reconciliation and uses its cancellation process. Choose one authoritative coordinator and verify Billing eligibility before release.
Validity versus expiryIf a non-expiring confirmed hold is adopted, Sales must distinguish confirmed validity from a technical authorization lease. Document lease semantics separately if introduced.
Dispatch/pickupUse exactly one agreed event for physical deduction. Delivery acceptance and proof of delivery do not by themselves constitute the chosen stock-deduction signal.

These decisions require code and test changes in the affected services. The Sales adapter has been updated and locally tested. This document does not make the proposed Inventory tables or external services live.

The appendix and companion System_1_2_3_Inventory_Proposed.sql extend the original System12 schema. They are a review proposal, not an installed migration or proof of MySQL execution.

Design choiceRationale
No changes to existing group-owned tablesThe proposal adds Inventory-owned tables only. Original offer/order/item/history identifiers and accepted snapshots remain intact.

Use a separate privileged migration account. Catalogue’s runtime account writes only Catalogue-owned data; Sales reads Catalogue and writes its own records; Inventory reads permitted references and writes only Inventory tables. Do not grant other modules UPDATE access to stock balances or movement history. Enforce append-only movement behavior with grants and controlled write paths.

12. Processing algorithms and acceptance tests

Reserve transaction

Authenticate → validate request hash/reference → lock order control → reject a cancellation tombstone → lock stock rows in stable order → verify all authoritative order-item mappings and active offers → check all available quantities → create all holds and increment reserved balances → save one immutable batch result and outbox entries → commit. A duplicate key returns the original stored result; a changed payload under the same key is a conflict.

Confirm, release and fulfillment

Confirm: verify Sales’ payment authorization under the agreed trust contract, lock the same records, require every original active hold to be eligible, and change all holds together. Release: create the order tombstone first, validate release eligibility, release all releasable holds and save the authoritative result. Fulfill: deduplicate the agreed Delivery event, verify order/item/stock/reservation links, reduce both balances, mark all holds fulfilled and append sale movements in one transaction.

Acceptance testPass condition
Last unit / concurrent requestsOnly one order reserves the last available unit; balance never becomes negative.
One short or inactive itemWhole request rejected; no partial hold or counter change. Product/offer IDs identify failures.
Repeated reserve / changed payloadIdentical retry returns identical IDs/result; altered body under same key is rejected.
Multi-item request / dispatchOne request can create multiple holds; one dispatch event can create multiple movements without duplicate deductions.
Release before reserve / duplicate releaseNo later hold can be created; release stays idempotent and counters do not double-decrease.
Confirm vs expiry; release vs fulfillOne legal serialized outcome; no expired/released hold is revived or shipped.
Payment/cancellation racePaid evidence is retained; Sales remains unresolved until reconciliation.
Stock audit and privilege checksEvery on-hand change has a matching immutable movement; Sales cannot update Inventory.
Existing purchase preservationCatalogue changes never rewrite submitted Sales names, prices or totals.

These are required joint tests for the proposed integration. Existing Sales tests use SQLite/simulators and do not substitute for MySQL/Inventory transaction tests.
